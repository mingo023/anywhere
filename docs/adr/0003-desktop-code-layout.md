# Desktop code layout: model crates, feature modules, state per feature

The desktop follows Zed's split. Model crates hold domain logic with no rendering and are unit-tested without GPUI; the `pocket` crate holds views. Inside `pocket`, each feature owns one module and a state struct that `Desktop` composes, instead of `Desktop` carrying every field. We chose this because `Desktop` had grown to ~90 fields touched from every file, so a change to the diff view risked the terminal, and none of the project/worktree rules could be tested. The cost: views still `impl Desktop`, so a feature reads shared state (`projects`, `repos`, `agents`) through `Desktop`; turning a feature into its own `Entity` is the next step, one feature at a time. The palette is the first.

## Rules

- A crate's lib is `src/<crate>.rs`; a module with children is `foo.rs` plus `foo/`. No `mod.rs`.
- Model crates never depend on `ui`, `theme` or `pocket`.
- A feature's state struct lives in its module, is built by its own `new`, and returns its own subscriptions. `Desktop::new` only composes them.
- Logic that only needs a feature's state is a method on that state, or a free function, with tests beside it. `impl Desktop` methods stay thin: gather inputs, call the logic, `cx.notify()`.
- One file per component. Split by component, not by size.
- A feature that is its own `Entity` owns its state, its render and its keys. `Desktop` hands it plain data each render (the palette's `sections`) and acts on the events it emits (`PaletteEvent`); the feature never reads `Desktop`. `Desktop` keeps the work that needs its state, such as building the data and running a pick.

## Map

|---|---|
| `pocket` | the binary: app bootstrap, window, the `Desktop` shell and feature views |

| `daemon` | the pocketd socket client |
| `agents` | the phone-socket client (`agents/link` the connection, `agents/outbox` what the desktop sends, `agents/event` what pocketd's frames decode to; `agents/summary`, `agents/items`, `agents/ask` and `agents/offered` the agent, its timeline, its asks and the commands and MCP servers it offers), the agent list, worktree display names, Locals, automations and the Board: the snapshot, the draft's validation and its messages; `agents/tickets` the Board's tickets; `agents/hosts` the machines pocketd links over SSH, as its `host.*` messages carry them; `agents/queue` each session's queue of held messages as pocketd lists it; `agents/delegations` the sessions a chat delegated to; `agents/providers` the built-in table of each provider (ids, efforts, plan, models, resume and fork args, status text, how to install it, how pocketd drives its chat, whether it never asks, reports status in a chat only or lists models under who serves them) plus what pocketd says it takes (efforts, plan, chat capabilities, never asks); `agents/catalogs` the models each newer agent's CLI lists, read from what it prints or answers |
| `term` | the ghostty VT |
| `store` | the saved projects, `store/sections` their pins and groups, settings (sounds, notifications, appearance, worktree root; `store/prefs` one struct per Settings section), `store/themes` the imported theme files, `store/backgrounds` the background image's copy in `~/.anywhere/backgrounds`, and each worktree's panels |
| `project` | which project and worktree a folder belongs to, the folders git refresh reads; `project/scratch` making a Scratch folder and what deleting one would lose; `project/open_in` the apps a folder can open in (macOS), which are installed and how each is launched |

| `web` | the WKWebView page of a browser tab, address and link parsing; `web/pick` the element picker's script and the element it posts |
| `chat` | an agent's chat as plain data: the transcript (turns, messages, tool calls, sub-agents) folded from the timeline, `chat/adapter` the `Backend` each agent provides and its capabilities (`adapter/claude`, `adapter/codex`, `adapter/acp` for the six pocketd drives over ACP, `adapter/pi` for pi and omp, `adapter/other` for a provider this build doesn't know), `chat/rows` the transcript's rows, `chat/session` one pane's transcript, rows and folds kept in step, `chat/spawned` the sub-agents the agent map shows, `chat/outgoing` sends, the queue and their settling, `chat/commands` the slash commands an agent offers and what the chat does with each, `chat/mcp` the MCP servers a draft tags and what picking one does, `chat/handoff` what a new chat is told when it takes over from another agent's, `chat/rich` a prompt's markdown as it is typed: what to style, and the edits that keep a list going, format a selection and read a paste |
