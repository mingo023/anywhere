# Team Mode: Plan Index and Contracts

Team mode lets one chat session, the **lead**, split a request into tasks. Each task runs as a **worker**: a chat session in its own worktree, nested under the lead. You edit and start the plan, answer the asks the plan didn't allow, and merge.

Background: `docs/orchestrators/product/08-orchestrator-mode.md` (design), `docs/spike-orchestrator-team.md` (what the spike proved), `.ui-review/prototypes/orchestrator-team.html` (UI, the **Island** variant).

The work ships as six plans, one PR each. This page holds the decisions and the contracts every plan builds on. A plan that needs to change a contract changes it here first.

| # | Plan | Ships | Depends on |
|---|---|---|---|
| 1 | `2026-11-05-team-mode-1-parent.md` | A session can have a parent. Workers nest under the lead in the sidebar, and their chat has a breadcrumb back | nothing |
| 2 | `2026-11-05-team-mode-2-mailbox.md` | A durable per-session mailbox in pocketd, delivered to Claude and Codex chats, acked only when the turn that showed it ends normally | nothing (inert until 4) |
| 3 | `2026-11-05-team-mode-3-plan.md` | `team: true` on a prompt makes the lead plan. pocketd parses and validates the plan block and publishes `team.update` | nothing |
| 4 | `2026-11-05-team-mode-4-run.md` | `team.start`, `team.stop`, `team.merge`: workers launch, hand back, get allowlisted asks answered, and merge; after a restart every team is reconciled | 1, 2, 3 |

## Decisions

- **Agents.** Lead and workers can each be Claude or Codex, in chat mode.
- **Trigger.** The composer's "+" button becomes a menu with **Attach images** and **Team**. **Team** adds a `Team ×` chip, and the next send carries `team: true`. Both composers get it: a running chat (`agent.prompt`) and a new session (`agent.create` spec, which then needs `chat: true` and a prompt). The desktop offers **Team** only when the connected pocketd negotiated the `team.v1` cap, and in a running chat sends a team prompt only while the agent is idle (the chip waits otherwise).
- **One team per lead.** A team prompt replaces the lead's team when it is `planning`, `proposed`, `merged`, `conflict` or `failed`. While it is `running`, `review` or `merging`, pocketd refuses the prompt with code `team_busy` and sends nothing. A lead that closes while its team is `planning` fails it with `the lead closed while planning`.
- **The user's text stays the user's.** The rules go before the user's text (`team.Wrap`), but every user timeline item starting with an `<anywhere_team>…</anywhere_team>` block loses it (`teamrules.Strip`, where Claude transcript and Codex `userMessage` items are mapped), so the chat and the session's title show only what the user typed.
- **The lead has no tools for the team.** It answers with a plan block. pocketd parses it. You click **Start**, and pocketd launches the workers as the owner. No grants (E15) are needed.
- **Models.** The lead picks the `agent` (`claude` or `codex`), not the model, because the models an account can use differ (the spike hit `model_not_found`). The plan sheet shows each task with the provider's default model, and you can change it.
- **Plan sheet edits.** Remove a task, change its agent or model, and edit its allowlist. Titles, instructions, files and `after` are fixed; to change them, ask the lead for a new plan. At most 4 workers run at once (`team.Parallel = 4`), not editable.
- **Allowlist.** Each task has `allow`: command prefixes the lead proposes and you approve at **Start**. When a worker asks to run a shell command, pocketd allows it without asking you only if the command is a single command (no `;`, `&&`, `||`, `|`, `&`, `` ` ``, `$(`, `>`, `<`, newline) and starts with an allowed prefix followed by a space or the end. Every other ask goes to you, as today. Each auto-allow is recorded in the worker's timeline as a notice.
- **Start.** `team.start` lists the tasks you kept, each with its agent, model and allowlist. pocketd refuses a list that drops a task a kept task lists in `after` (`Task t3 starts from t1's work; keep t1 or remove t3 too`; plan 6's sheet already prevents it), and the kept tasks must pass `ValidateKept`: every rule of `Validate`, but 1 to 4 tasks, so you can start just one. The lead's plan itself still needs 2 to 4 (`Validate`). Plan 6's sheet enables Start with one kept task.
- **Worktrees and branches.** Each worker gets a new worktree and a branch of the same name. `team-<lead6>-<task>` is the preferred name, where `<lead6>` is the first 6 characters of the lead's agent id. When a task starts, pocketd picks the first of `name`, `name-2`, `name-3`, … that is neither an existing branch (local or remote) nor a folder in the project's worktrees folder, whose `<name>-base` is free too, and that no other task of the team holds, and stores it in `TeamTask.Branch` (the worktree in `TeamTask.Worktree`). Everything after reads the stored name. A task with no `after` starts from the lead's HEAD **commit** (not its branch name, which `Plan.Fetch` could move to `origin/<branch>`). A task with one `after` starts from that task's branch. A task with several `after` starts from `<its branch>-base`, which pocketd makes by merging those tasks' branches without a checkout (`git merge-tree --write-tree`, git ≥ 2.38); a conflict there fails the task and tells the lead.
- **Workers.** pocketd launches each worker as the owner with no prompt, records it on its task, names it after the task's title, and only then sends the assignment, so a fast turn can't end before pocketd knows whose it is.
- **Handback.** Every turn of a worker that ends normally (not failed, not stopped by the user) makes pocketd commit everything in its worktree (`git add -A`, `git commit --no-verify -m "team <task>: <title>"`, skipped when clean) and mail the lead a handback with `git diff --stat <base>...HEAD` (three dots: what the branch changed since it left its base). A failed turn or a closed worker marks the task failed, with the reason in `TeamTask.Summary`, and mails the lead.
- **Notes.** When you prompt a worker directly, pocketd also mails the lead a note that starts `The user told worker <task>:`. The spike showed that "You told…" makes the lead think it said it.
- **Verdict.** After every task has handed back, the lead's next turn end is read. If its last text contains "Ready to merge" (case-insensitive) other than right after "not" or "n't" (the spike's lead said "Not ready to merge"), the team is `ready`. Every later ok turn end of the lead in review is read again. **Merge** works either way but warns when the team isn't ready: the spike's merge was clean and tests passed while the work was wrong.
- **Merge.** pocketd merges each task branch with `git merge --no-ff` into the lead's checkout, in dependency order. It refuses when that checkout has uncommitted changes to tracked files. On a conflict it runs `git merge --abort`, stops, records the files, and mails the lead. After a full merge it closes the workers, removes their worktrees and keeps the branches.
- **The lead needs you while its plan waits.** While a team is `proposed`, pocketd marks the lead's agent as awaiting the user (`Agent.SetAwaiting`, set by `Teams.change`), so its status reads `needsYou` everywhere: the sidebar card, banners, the Dock badge, the phone. It clears when the team leaves `proposed` or the lead's next turn starts. Keep-awake, account switches, terminal input and pocketd's turn checks ignore the wait (they read `Agent.Turn`), so a waiting plan neither keeps the Mac awake nor holds a switch. The desktop overrides no status; the sheet still opens by itself.
- **Restart recovery.** Once pocketd is back and the restored sessions have come back or failed (`Daemon.WaitRestored`), `Teams.Recover` reconciles every team that was planning, running, in review or merging. A worker that is back shows its status, or hands back if its last turn ended normally and that turn wasn't handed back already: `TeamTask.turn` records the prompt id of the turn last handed back, so a turn end heard twice hands back once, and recovery queues its handbacks on `Run` like any turn end. A worker that is gone fails its task with Summary `the worker stopped when pocketd restarted`, and the lead is mailed the failed handback. A team stuck `merging` aborts a merge in progress (`git merge --abort`) in its recorded checkout (`Team.checkout`, set when the merge starts, so the lead needn't be back) and shows `conflict` with Error `pocketd restarted during the merge`; with no merge in progress it goes back to `review` with that Error. A `planning` team whose lead is gone fails (`the lead stopped when pocketd restarted`); one whose lead is back and idle has its last turn read again. `Run` handles nothing once shutdown starts, so closing sessions doesn't fail tasks.
- **Refused team requests are toasts.** An `error` answering `team.start`, `team.stop` or `team.merge`, or refusing a team prompt (`team_busy`), becomes `Event::TeamFailed` on the desktop (plan 5), shown as a toast naming the action and pocketd's message (plan 6). A refused team prompt also fails its send in the chat.
- **Retry keeps the team flag.** A failed team send remembers it asked for a team, and its Retry sets the `Team ×` chip again (plan 5).
- **Storage.** SQLite, as `internal/skills/store.go` does (`modernc.org/sqlite`, `SetMaxOpenConns(1)`): `state/mail.db` for the mailbox and `state/team.db` for teams. Both survive a pocketd restart. Mail that was shown but not acked goes back to the queue on start.
- **One team engine.** `team.Teams` (plan 3, extended by plan 4) is the only code that changes a team. Every write goes through `Teams.change` (one mutex: read, apply a pure decision, `Store.Put`, publish `team.update`). Hooks that run under an agent's lock (`OnStatus`, `OnTurnEnd`) only queue an event; `Teams.Run` handles the queue in order on one goroutine.
- **Wire mirrors.** Every wire change lands in Go (`internal/proto`), TypeScript (`packages/protocol`) and Swift (`packages/ios/Packages/AnywhereKit/Sources/Wire`) in the same PR: the TS and iOS golden tests decode every pocketd golden, client and server.
- **Out of scope.** The phone (it only decodes the wire), grants, hiding worker worktrees from the sidebar's tree list, and enforcing `files` with a `PreToolUse` hook.
- `CONTEXT.md` gains **Team**, **Lead**, **Worker**, **Handback** and **Mailbox** (plan 3). Never call a team's work a "run": **Run** means one firing of an automation.

## Contracts

### Wire (pocketd ⇄ clients)

`proto.LaunchSpec` gains two optional keys. Both must be added to the `decodeSpec` allowlist:

```go
Parent string `json:"parent,omitempty"` // lead's agent id (plan 1)
Team   bool   `json:"team,omitempty"`   // the first prompt asks for a plan (plan 3)
```

`LaunchSpec.Team` needs `chat: true` and a non-empty `prompt`; otherwise `invalid_spec`, "A team starts from a chat session's first prompt" (plan 3).

`proto.AgentSummary` gains `Parent string `json:"parent,omitempty"`` (plan 1). It stays comparable.

`agent.prompt` gains `team` (bool, optional; plan 3): `{"type":"agent.prompt","id","agentId","text","team":true}`. Refused with code `team_busy` (`proto.CodeTeamBusy`) while the lead's team is `running`, `review` or `merging`.

Cap `team.v1` (`proto.CapTeam`, in `ServerCaps`, plan 3): pocketd plans and runs teams. Clients offer **Team** only when it is negotiated.

New client verbs:

| Verb | Fields | Scope | Plan |
|---|---|---|---|
| `team.list` | `id` | observe | 3 |
| `team.start` | `id`, `lead`, `tasks: [TaskPick]` | spawn | 4 |
| `team.stop` | `id`, `lead`, `task` | drive | 4 |
| `team.merge` | `id`, `lead` | spawn | 4 |

`team.start` lists the tasks you kept, as `TaskPick {id, agent, model?, allow?}` (`id` and `agent` required; an absent `allow` is an empty allowlist). A task left out is removed. `team.list` replies `{"type":"team.list","id","teams":[Team…]}`. The others reply with the usual ack or error.

New server event: `{"type":"team.update","team":Team}`, published on every change.

```go
// package proto
type Team struct {
	Lead      string     `json:"lead"`
	State     string     `json:"state"` // planning | proposed | running | review | merging | merged | conflict | failed
	Error     string     `json:"error,omitempty"`
	Tasks     []TeamTask `json:"tasks"`
	Ready     bool       `json:"ready,omitempty"`    // the lead said "Ready to merge"
	Conflict  []string   `json:"conflict,omitempty"` // files of the failed merge
	Repaired  bool       `json:"repaired,omitempty"` // the one repair turn was used
	Checkout  string     `json:"checkout,omitempty"` // the lead's checkout a merge runs in (plan 4)
	UpdatedAt int64      `json:"updatedAt"`          // Unix ms
}

type TeamTask struct {
	ID           string   `json:"id"`
	Title        string   `json:"title"`
	Agent        string   `json:"agent"` // claude | codex
	Model        string   `json:"model,omitempty"`
	Files        []string `json:"files"`
	After        []string `json:"after"`
	Allow        []string `json:"allow"`
	Instructions string   `json:"instructions"`
	State        string   `json:"state"` // planned | waiting | running | needsYou | done | failed | stopped | merged
	Worker       string   `json:"worker,omitempty"` // worker's agent id
	Branch       string   `json:"branch,omitempty"`
	Worktree     string   `json:"worktree,omitempty"`
	Summary      string   `json:"summary,omitempty"` // worker's last text; a failed task's reason
	Stat         string   `json:"stat,omitempty"`    // git diff --stat <base>...HEAD

}
```

States: `planning` (team prompt sent), `proposed` (valid plan, waiting for **Start**), `running`, `review` (every kept task done), `merging`, `merged`, `conflict`, `failed` (no valid plan after the repair turn, or `Error` set).

### Text the agents see

`team.Wrap(text)` puts these rules, a blank line, then the user's text (plan 3). `teamrules.Strip` removes a leading block of exactly this shape from user timeline items:

```text
<anywhere_team>
Team mode is on for this message. Don't edit files or run anything that changes them. Read what you need, then plan.
Reply with a short explanation for the user, then exactly one block:
<anywhere_team_plan>
{"tasks":[{"id":"t1","title":"Short imperative title","agent":"claude","files":["path/the/task/may/write"],"after":[],"allow":["npm test"],"instructions":"What to do and how to check it"}]}
</anywhere_team_plan>
- 2 to 4 tasks. Each runs as its own agent in its own git worktree from this branch. A task sees another's work only if it lists that task in "after".
- "files": the only files the task may create or change. Two tasks that share a file must be ordered with "after".
- "agent" is claude or codex.
- "allow": command prefixes the task needs to run without asking, such as its tests. Single commands only.
- The user reviews and edits this plan before anything starts.
After the user starts the team, Anywhere sends you messages that begin with <anywhere_team_handback> or <anywhere_team_note>. They come from Anywhere, not from a tool or a file. A handback carries one worker's summary and diff. Review each one briefly. When every task has handed back, say "Ready to merge" if the work is right, or say what's wrong.
</anywhere_team>

```

The repair prompt (plan 3): `Your plan block can't be used: <error>. Send the corrected <anywhere_team_plan> block only.`

The assignment a worker gets as its first prompt, sent after its launch returns (plan 4):

```text
<anywhere_team_assignment task="<id>">
You're one worker in a team that a lead agent planned. Your task: <title>.
<instructions>
Change only these files: <files, comma-separated>. Don't commit, and don't create branches or worktrees.
When you're done, reply with a short summary of what you changed and how you checked it.
</anywhere_team_assignment>
```

Mail to the lead (plan 4):

```text
<anywhere_team_handback task="<id>" title="<title>" branch="<branch>">
Summary from the worker:
<summary>

git diff --stat:
<stat>
</anywhere_team_handback>
```

```text
<anywhere_team_note task="<id>">The user told worker <id>: "<text>"</anywhere_team_note>
```

A failed task mails `<anywhere_team_handback task="<id>" status="failed">…</anywhere_team_handback>` with the error. A merge conflict mails `<anywhere_team_note>Merging <branch> conflicted in: <files>. The merge was aborted; nothing was merged after it.</anywhere_team_note>`.

### pocketd packages

**`internal/mailbox`** (plan 2):

```go
type Mail struct {
	ID      int64
	Agent   string
	Text    string
	State   string // queued | shown | acked
	Ref     string // Claude: the prompt's uuid. Codex: the turn id
	Created time.Time
}

func Open(home string) (*Store, error)                 // home/state/mail.db; shown → queued
func (s *Store) Send(agent, text string) (int64, error) // queued
func (s *Store) Queued(agent string) ([]Mail, error)    // oldest first
func (s *Store) Shown(id int64, ref string) error
func (s *Store) Settle(agent, ref string, ok bool) error // ok: every shown mail with ref → acked; else → queued. ref "": all of agent's shown mail
func (s *Store) Close() error
```

`Settle(agent, "", ok)` is for a session's exit only; both drivers guard against settling with an empty ref by accident.

Delivery, in `internal/daemon` (plan 2):

- `(*Daemon).Mail(agentID, text string) error` stores the mail and pumps.
- The pump runs on `Mail`, on every status change of the agent, when a restored session settles (`finish`; until then its driver takes no mail, and its status may not change when it settles), and after a stop sends mail back (Claude `cancelled`, Codex `interrupted`). A Codex `failed` turn's mail goes back to the queue but waits for the next status change, so a model that keeps failing doesn't loop. It delivers every queued mail of an agent whose status is `idle`, `working` or `done`, and holds it while the agent is `needsYou`, closed, or not a chat.
- Drivers gain `Deliver(text string) (ref string, err error)`, as the optional interface `agent.Deliverer`:
  - Claude writes `promptLine` with a fresh `uuid` (the ref), `session_id: ""` and `parent_tool_use_id: null`. Only mail lines carry a `uuid`; prompts typed in the chat don't, so they produce no `command_lifecycle` lines.
  - Codex calls `turn/start` when idle, and `turn/steer` with `expectedTurnId` once pocketd has heard the running turn's `turn/started`. In the short time before that, it calls `turn/start`, which the app-server steers into the running turn. Either way it returns the turn id from the response.
- Settling:
  - Claude: a `command_lifecycle` line with `completed` settles that uuid ok; `cancelled` settles it not ok.
  - Codex: `turn/completed` with `status: completed` settles that turn id ok; `interrupted` or `failed` settles it not ok.
  - A session that exits settles all its shown mail not ok.

### Desktop crates (plans 1, 5, 6)

- `agents::Summary` gains `pub parent: String` (plan 1). `hosts::session::tag_summary` tags it like `id`.
- `agents::team` holds `Team`, `TeamTask` (`#[derive(Deserialize, Clone, Debug, Default, PartialEq)]`, serde `default`, camelCase; states as `String`; `updated_at` is Unix ms) and `TaskPick { pub id, pub agent, pub model, pub allow }` (`#[derive(Serialize, Clone, Debug, PartialEq)]`; an empty `model` or `allow` is left off the frame, like Go's `omitempty`), re-exported as `agents::{Team, TeamTask, TaskPick}` (plan 5).
- `agents::Event::Team(Team)` replaces its lead's team unless the one held is newer (`updatedAt`). `Event::Teams(Vec<Team>)` replaces every team of the pocketd that sent it (a team in the list still loses to a newer one held); `Teams(vec![])` clears them. `Agents::team(&self, lead: &str) -> Option<&Team>` reads one; `Agents::forget(host)` drops a host's (plan 5).
- `agents` sends `CAPS` with `team.v1`; `Agents::teams_offered()` is true when it was negotiated and the conn isn't observe-only. `agents::run` sends `{"type":"team.list","id":"teams"}` after every `hello.ok` that negotiated `team.v1` (this Mac's and each host's connection) (plan 5).
- `Outbox::prompt(agent_id, text, team: bool)`: `"team"` is on the frame only when true. `Outbox` gains `team_list()`, `team_start(lead, &[TaskPick])`, `team_stop(lead, task)`, `team_merge(lead)`; team verbs go out with ids `team-<n>` (plan 5).
- `agents::TeamAction { Plan(String), Start, Stop, Merge }` (re-exported) and `Event::TeamFailed { lead, action, message }`: a refused or unsent team prompt (`Plan` carries its request id) or team verb, `message` as `readable` makes it; tagged by `lead` (plan 5). `pocket::team::failed(action, message)` is the toast's text (plan 6).
- `chat::Outgoing::asks_team(id)` marks a send as a team send; `Outgoing::retry(id) -> Option<(String, bool)>` hands back its text and whether it asked for a team (plan 5).
- `hosts::session::tag_event` tags a team's `lead` and each task's `worker` (ids, as `Summary.id`) and `worktree` (`//host/path`). `Outboxes` gains `team_start/team_stop/team_merge`, routed by the lead's host tag, which is what `pocket` calls (plan 5).
- `pocket::composer::Draft` gains `team: bool`, drawn as the `Team ×` chip (plan 5).
- The lead's **Needs you** while its team is `proposed` comes from pocketd's status (plan 3); the desktop adds no override. `pocket::team::plan::can_start(proposed, kept)` enables Start with 1 or more kept tasks (plan 6).
